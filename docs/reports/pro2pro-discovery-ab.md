# Discovery A/B: XploreMore-sourced vs HN/web-sourced (P6)

**Status: complete, 16/16 trials, 2026-09-17/18.** The headline finding is not "XploreMore
problems score lower" — it's that **on this Groq tier, adding XploreMore's two extra tools
pushed more research turns past the token-rate ceiling before they could finish**, which is
what actually drove the gap below. See "Interpretation" before drawing any conclusion from the
table.

## Question

Pro2Pro's Research Agent can discover problems from XploreMore's clustered, demand-ranked
problem API, or from its own Hacker News and web search. Does the XploreMore source produce
better discovery for the same budget?

## Design

One trial = one topic, one arm, running the **real** Research Agent and the **real** Analyst
(guardrails → dedupe → conviction score). 8 topics × 2 arms = 16 trials.

- **`xploremore` arm:** `XPLOREMORE_API_URL` set, so `find_problems`/`get_problem` are bound
  alongside the HN/web tools, with the XploreMore prompt.
- **`baseline` arm:** `XPLOREMORE_API_URL` unset, so exactly the pre-existing HN/web toolset
  and prompt.

Held equal across arms: provider and model, `max_tokens`, guardrails, the Analyst prompt and
its shortlist threshold, the research step ceiling (both arms get 22, so the baseline is never
cut short where the XploreMore arm would not be), the turn timeout, the per-call retry policy,
and a 65 s pause before every trial so each one starts with a fresh tokens-per-minute window.

Arm order alternates by topic, so any drift in provider latency or rate-limit state does not
systematically favour one arm. Each arm keeps its own dedupe memory, so "dedupe-new" means new
relative to that arm's own earlier trials. No trial writes to the application database and no
review email is sent.

**Topics** (`evals/pro2pro/topics_v1.txt`) were fixed before the first trial and were not
tuned on results.

## Statistics

- Proportions over trials (for example "research turn completed") use a Wilson 95% interval.
- Idea-level metrics (guardrail pass rate, dedupe-new rate, shortlisted share, conviction,
  tokens per shortlisted idea) use a **cluster bootstrap that resamples whole trials**, because
  ideas from one research turn are not independent of each other.
- Differences between arms are computed **paired by topic**, bootstrapped over topics.
- 10,000 resamples, seed 7, so the intervals are reproducible.

## What this cannot tell you

- **Sample size is small** (8 topics per arm). Intervals will be wide; treat anything whose
  interval spans zero as "not distinguished by this experiment".
- **The Analyst is an LLM, not ground truth.** Conviction and shortlisting measure what the
  Analyst thinks, which is what actually gates Pro2Pro's pipeline, but it is not a measure of
  real-world problem quality.
- **Approval share and human quality ratings are not measured**, because they need a human.
  They are reported as "not measured" rather than replaced with a proxy.
- LLM output is stochastic and each cell here is one run per topic, so re-running will not
  reproduce the numbers exactly. The raw per-trial data is committed so any claim can be
  recomputed.
- XploreMore's side is a **one-day dev corpus snapshot** whose classifier and clustering
  quality are themselves provisional and assistant-audited (see `docs/problems.md`). The
  baseline arm searches the live web. This is a comparison of two discovery paths on this
  corpus, not a general claim about either source.
- Both arms ran on Groq's 8,000 TPM tier, where a turn can spend minutes waiting out rate
  limits. Wall-time differences mostly reflect that ceiling, not the sources.

## Reproduce

```bash
# XploreMore API with a key, from the xplore_more repo
PORT=8765 uv run xm-api
uv run xm-api keys create --name pro2pro-local --rate 600

# from the p2pagent repo (commit cbdf5ab)
XPLOREMORE_API_URL=http://127.0.0.1:8765 XPLOREMORE_API_KEY=<key> \
  uv run p2pops-discovery-ab run \
    --topics-file ../xplore_more/evals/pro2pro/topics_v1.txt \
    --out ../xplore_more/evals/pro2pro/ab_v1.jsonl --data-dir <scratch dir>
uv run p2pops-discovery-ab report --in ../xplore_more/evals/pro2pro/ab_v1.jsonl
```

Raw per-trial data: `evals/pro2pro/ab_v1.jsonl` (one JSON object per trial: tools bound, every
tool call, XploreMore availability and any outage, each idea with its status, score and
provenance, token counts, rate-limit retries, wall time).

## Interpretation

**Read the failed-trial detail before the topline numbers.** Of 16 trials, 4 failed to complete
a research turn at all:

| Arm | Topic | How it failed | Wall time |
|---|---|---|---|
| xploremore | RAG retrieval quality | `TimeoutError` (240 s turn ceiling) | 243.5 s |
| xploremore | running local LLMs | `TimeoutError` (240 s turn ceiling) | 240.0 s |
| xploremore | observability for LLM apps | `TimeoutError` (240 s turn ceiling) | 240.0 s |
| baseline | Kubernetes deployments | `RuntimeError` after 1 attempt (non-retryable, not a timeout) | 228.7 s |

**3 of the XploreMore arm's 8 trials (38%) failed specifically by running out the 240 s turn
timeout; 0 of the baseline arm's trials did.** A failed trial reports 0 ideas and 0 shortlisted,
which mechanically drags down every per-trial average for that arm — "ideas per trial",
"shortlisted per trial" and "wall time per trial" are all pulled toward the failure case.

The mechanism is visible in the raw logs, not inferred: the XploreMore arm's prompt budgets two
more tool calls than baseline (`find_problems`, optionally `get_problem`), each one an extra
model turn on Groq's `gpt-oss-20b` **8,000 tokens/minute** on-demand tier (re-measured
2026-09-15, ADR-0012 in `p2pagent`). More turns before the model can answer means more chances
to hit the per-minute ceiling mid-run, and each rate-limit wait can be 20–45 s. Three XploreMore
trials logged 8–9 rate-limit waits each and simply ran out of the 240 s budget before the model
produced a final answer — this is a **provider-tier and token-budget effect**, not evidence that
the problems XploreMore found were worse. In fact, of the XploreMore trials that *did* complete,
XploreMore-sourced ideas still carried through to 67% of all reported ideas having verified
provenance (problem id, voices, sources) — exactly the mechanism ADR-0012 was built to prove
works, and it did, whenever the turn had budget to finish.

The Analyst-conviction gap (40.9 vs 75.8) is harder to attribute cleanly: it could be the
Analyst genuinely finding the XploreMore-sourced ideas less compelling, or it could inherit the
same selection effect (the completed XploreMore trials may be a biased sample — the easier,
shorter turns that didn't hit the ceiling). With only 8 topics per arm and 3 XploreMore failures,
this experiment cannot separate those two explanations. That would need either a materially
higher-TPM provider tier (removing the confound) or a larger sample with today's tier (to see
whether conviction still differs among *completed* trials only) — both are follow-up work, not
something to resolve by re-reading these 16 rows harder.

**What this experiment does support:** the code-level fallback and provenance mechanism (ADR-0012)
work as designed — 0 XploreMore-configuration failures, 0 hallucinated provenance, compact
results throughout. **What it does not support:** any claim that XploreMore-sourced problems are
better or worse than HN/web ones for the Analyst — the dominant effect measured here is a token
budget ceiling on a specific free-tier provider, not the discovery source.

## Recommended follow-up (not done here)

1. Re-run this exact harness on a provider tier with materially more headroom (Anthropic direct
   or a paid Groq tier), to remove the timeout confound.
2. If the completion-rate gap persists on a higher tier, that would be real evidence about the
   XploreMore prompt/toolset's cost, not an artifact of this provider.
3. A larger topic sample restricted to trials that completed, to test the conviction gap in
   isolation from the timeout selection effect.
